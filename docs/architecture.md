# How it works

**English** | [日本語](ja/architecture.md)

Worktabs is an Electron app. It starts a code-server for each worktree, shows it as a tab, and receives conversation state through Claude Code hooks and Codex app-server events. The research and verification behind the design are in [research.md](research.md) (English).

## Repository refresh

`src/commands.js` owns the shared local and WSL command adapter. Clone, task, GitHub, and agent CLI code use it directly. It preserves stdin, cwd, explicit environment overrides, timeouts, output on failure, and hidden Windows processes. WSL commands keep the distribution's shell environment and Linux paths. `src/repos/worktrees.js` retains compatibility exports while keeping repository discovery and Git worktree operations separate from the adapter.

`src/repos/github.js` keeps the app's shared GitHub client API. `src/repos/github-client.js` creates clients with injected command and Git readers. Each client owns configured hosts, SSH hostname lookups, and signed-in host caches. GraphQL calls share command construction and JSON handling. Branch PR reads require a successful response; visibility and approved-PR reads may use partial data from a failed GraphQL response.

Repository discovery and GitHub metadata are coordinated by `src/repos/repository-service.js`. It owns `repos.json` snapshots and numbered sidebar messages. Catalog requests coalesce; an explicit refresh or an addition during a read schedules one more read. Clone additions appear immediately and survive an older catalog result. Failed sources keep their previous entries; successful empty sources clear them. Removed catalog entries lose cached remotes and unread worktrees.

Visibility reads run one at a time, with one follow-up when requested meanwhile. Owned repository results are published after remote and renamed-address matching. A failed GitHub host keeps its last owned result. Approved-PR refreshes combine follow-up requests so an explicit `all` read is not lost. Periodic reads query only running WSL distributions and keep sleeping distributions' marks. Explicit catalog and `all` reads may start WSL. Menus (`src/window/menus.js`), clone dialogs, and IPC (`src/window/ipc-table.js`) call the service; `main.js` keeps their Electron concerns.

## Tab lifecycle

`src/conversations/conversation-opening.js` coordinates row clicks, helper registration, pending navigation deadlines, first-conversation dispatch, and restoration warnings. It receives tab and server-start identity readers, helper calls, and timers. The lifecycle delegates pending-reveal cancellation on tab switching and cleanup; Electron keeps frame execution and native dialogs in its adapter. Mounted Codex thread confirmation and first-task draft handling remain in their existing modules.

`src/repos/worktree-removal.js` coordinates removal checks, confirmation ownership, tab closing, worktree and branch deletion, and storage cleanup. It receives Git readers, conversation and tab state, dialogs, and native operations. Blockers and existing read-failure fallbacks are preserved. The primary opens before removal; failed removal keeps the worktree's retained storage, while successful removal clears it before optional branch deletion. Branch recovery notifications remain in the Electron adapter.

`src/tabs/tab-lifecycle.js` owns open tab identities, their order, the active tab, and server start and stop transitions. `src/main.js` supplies the Electron views, server managers, risk dialogs (`src/tabs/tab-risks.js`), settings sharing, and file and cookie storage (`src/tabs/tab-store.js` keeps tabs.json). The lifecycle can be tested without Electron.

- Closing a tab invalidates its pending start. Git lookup, server preparation, progress, and cookie completion from an old tab cannot update a reopened tab of the same folder.
- Starts of the same tab ID wait for the previous start to finish and release its server. An old start cannot stop a replacement server. Each manager returns the start's owner with its exit event, so an old exit cannot mark a replacement as stopped.
- Close, suspend, restart, startup failure, and server exit clear agent and helper runtime state through one adapter. Codex history stays when an open tab stops; closing removes it. The tab's reveal timer is cleared even after it leaves the open tab map.
- Confirmation and chat-width reads belong to the captured tab and server start. If either changes while the app waits, the action does not apply to its replacement. Closing a group picks the next active tab once and never starts another tab in that group on the way.
- The lifecycle builds and restores the tab part of `tabs.json`, using `src/tabs/tab-ports.js` for retained ports. The main process keeps repository use and chat widths in the same file. Restored background tabs remain suspended, and only the active tab starts. Provider and Codex history metadata are restored before the active tab starts.
- Saved tabs are restored before the sidebar can save new tabs. `src/tabs/startup-gate.js` holds all tab starts until code-server, the process wrapper, required extensions, and the language pack are prepared. The lifecycle selects a manager only after this shared wait. Closing or restarting a waiting tab cancels its own start without canceling preparation for other tabs. Startup failure reaches waiting and later tabs as an error, and no server starts with an incomplete install.

## code-server

Extension selection and import orchestration live in `src/code-server/extension-management.js`. It owns candidate keys, compatibility checks, previous-version staging, import and rollback requests, and gallery follow-up after a successful import. Discovery, server operations, version reads, scheduling, and update state are injected. Native file selection and opening desktop VS Code are in `src/window/settings-actions.js`, which takes the native picker from `main.js`. Staging errors occur before an update transaction starts, so they do not stop running tabs or replace installed extensions.

Update transactions use `src/code-server/update-coordinator.js` for preparation, idle waiting, cancellation, and the shared tab pause/resume boundary. Starts requested during the switch wait until it finishes. The coordinator resumes every surviving captured tab after success or failure, and an older canceled transaction cannot publish progress into a new one. A tab that starts during the idle check prevents the switch. Active Codex tabs whose turns cannot be observed still block updates.

Gallery installation and restoration live in `src/code-server/update-strategies.js`. New code-server settings are committed only after the local probe, and the previous release stays for manual recovery. WSL failures are reported separately. Imported snapshots use `applyImportBatch` in `src/code-server/extension-imports.js`; Linux imports still apply when the matching distribution next starts. The unused deferred-restart timer has been removed: the current workflow pauses idle tabs before installing and resumes them after the transaction.

The app starts one process per worktree (listening only on `127.0.0.1`).

- Each worktree has its own `user-data-dir`; the extensions folder is shared. VS Code settings are shared among the tabs of the worktrees of the same repository ([below](#sharing-vs-code-settings)).
- Authentication uses `--auth password`. On each start, the app passes a random value in `HASHED_PASSWORD` and writes the same value into the tab's cookie directly. Without this cookie, nobody can access the server. No plain-text password exists, so nobody can log in through the login page either.
  - code-server removes `HASHED_PASSWORD` from its own environment after it starts, so extensions and claude do not receive it.
  - Cookies are not separated by port, so `--cookie-suffix` gives the cookie a different name for each instance.
- VS Code's built-in AI features (the Copilot chat) are off by default (`chat.disableAIFeatures`). This removes the agentHost and copilot-runtime that each instance used to start, and cuts memory use by about 30%. The built-in chat that VS Code shows in the right side bar becomes empty, so the app replaces it with the Claude Code chat panel ([below](#helper-extension)).
- The VS Code color scheme follows the OS light or dark mode (`window.autoDetectColorScheme`).
- These two are instance defaults, so you can change them in the VS Code settings.
- The display language is passed with `--locale`, always: without it, code-server would follow the browser's language with whatever language packs the extensions folder has. It is the `locale` setting, or the app's UI language when that is empty, and its language pack is added to the extensions to install (`displayLocale` and `withLanguagePack` in `src/i18n/index.js`). code-server builds the list of language packs it uses for translation (`languagepacks.json`) only when an extension is installed from inside VS Code. The app installs extensions from the command line, so it writes this file for each instance on every start.
- Each worktree keeps a fixed port, saved in `tabs.json`. VS Code Web saves the state of the window (open files, Claude conversations in editor tabs, side bar views, panel sizes) in the browser per origin (port), so if the port changes, the previous window cannot come back (`src/tabs/tab-ports.js`).
  - When you close a tab, the app keeps its port. When you open it again, it starts on the same port, so the window comes back as it was before closing.
  - Remembered ports are not used for other tabs. If two tabs had the same origin, the state VS Code keeps regardless of folder (global) would mix between them. When the app takes a new port and the OS hands out a remembered one, it takes another. The same applies to the code-server started for update checks.
  - If another program is using a remembered port, the tab starts on a new port. The window starts empty, and the old port is forgotten.
  - A port is forgotten when you remove the worktree from the app, when its folder is gone at start (removed outside the app; WSL folders are not checked), and when there are more than 200 closed tabs (the least recently used first).
  - The storage of a forgotten port's origin (IndexedDB and so on) is cleared, so that a tab that later takes that port does not inherit the old window. Cookies are not cleared. Cookies are not separated by port, so clearing them would also clear the cookies of other tabs.
- The default redirect of code-server on Windows (`?folder=C:\...`) does not open, so the app builds the URL in the `?folder=/c:/...` form.
- Before starting, the app removes environment variables such as `CLAUDECODE`, `CLAUDE_CODE_*`, `VSCODE_*`, `ELECTRON_*`, and `CODE_SERVER_*`.
- Links to a port on `localhost` open as they read: the URL a dev server prints in the terminal, and "Open in Browser" on the notification VS Code shows when a server starts on a port.
  - VS Code assumes the browser may be on another machine than the server, and turns such a link into an address the browser can reach (`resolveExternalUri`). code-server does this with its own proxy: `http://127.0.0.1:<code-server port>/proxy/<port>/<path>`. That needs code-server's login, which the default browser does not have, and it strips the start of the path, which breaks apps that load absolute paths.
  - The app turns such a link back into `http://localhost:<port>/<path>` before it opens it in the browser (`unproxiedUrl` in `src/code-server/code-server.js`). Only links to the proxy of the tab's own code-server are changed. A dev server in WSL is reached from Windows through WSL's localhost forwarding, as the app reaches code-server there.
  - code-server's template for the proxy (`VSCODE_PROXY_URI`) cannot point at the port itself instead. Its page reads the template as a URL, and `http://localhost:{{port}}` is not one: the workbench fails to connect with "Invalid URL".

## Code-server launch policy

`src/code-server/code-server-launch.js` owns common arguments, random cookie authentication, locale, managed settings and agent launcher preparation, language packs, and readiness waiting. Local and WSL managers use injected transport and health dependencies for contract tests. A readiness reply is accepted only while its captured instance is still current. Startup failures and stops release the settings-sharing handle once; a late failure cannot stop a replacement instance. An exit during startup rejects the start, while an unexpected exit after readiness carries its start owner. Local process groups and WSL agent requests, distribution preparation, Linux extension selection, and preferred-port retry remain in their backends. The neutral module also holds the shared port and URL helpers; `code-server.js` keeps their existing exports.

## Sharing VS Code settings

Tabs of worktrees of the same repository (main worktree) share `settings.json`, `keybindings.json`, `tasks.json`, `mcp.json`, `snippets/`, and `prompts/` in `User/` of the `user-data-dir` (`src/code-server/settings-sync.js`). They are not shared with tabs of other repositories or with tabs of folders that are not git repositories.

- The app does not use one `user-data-dir` per repository, because the code-servers of the same repository would then write `logs/`, `coder.json`, and `globalStorage/` at the same time. It does not link `User/` or the files either. Junctions work only for folders, hard links break depending on how a file is saved, and symbolic links need developer mode or administrator rights. None of them work for WSL tabs.
- The shared content is kept in `repos\<repository ID>\` in the data folder (the ID is a hash of the main worktree's path). Content for repositories in WSL is kept here too.
- Before starting a tab's code-server, the app writes the shared content into the tab's `User/`. So when a tab opens, the app waits until it has found the main worktree, then starts the server.
  - For `settings.json`, the app first adds the defaults the shared settings do not have (such as `chat.disableAIFeatures`) to the shared settings, writes the file, and then overwrites it with the settings the app manages (`claudeCode.claudeProcessWrapper` and `claudeCode.initialPermissionMode`).
- While a tab runs, the app watches its `User/`, `snippets/`, and `prompts/` folders. On a change, it waits 0.3 seconds, takes into the shared content what changed since the last sync, and passes it to the other running tabs of the same repository.
  - code-server does not reload changes in `User/` that it did not write itself. Rewriting `settings.json` from outside does not change the window (checked on a real Windows machine; it does read the file at start). So for running tabs, the helper extension writes the settings through the VS Code settings API (`WorkspaceConfiguration.update`) (`/settings`). VS Code writes `settings.json` itself and applies it at once. The theme changes too, the helper extension reports it, and the sidebar colors follow.
  - For tabs whose helper extension is not running yet, and for settings VS Code could not write (such as keys no extension registers), the app writes `settings.json` itself. They take effect on that tab's next start.
  - `settings.json` is synced key by key. Removed keys are removed too. If two tabs change different keys, both changes stay. If they change the same key, the value from the tab that changed it last wins.
  - The app does not write a key (or, for other files, the file) into a tab that has changes not taken in yet. It takes them in next and spreads them to the other tabs.
  - `settings.json` with comments (JSONC) is read too (`src/code-server/jsonc.js`). When writing, the app rewrites only the changed keys, so other lines and comments stay.
  - Tabs with a `settings.json` that cannot be read (half written, for example) are skipped until it can be read. An empty file, or no file, is also treated as being written, and nothing is removed.
  - Other files are copied whole. The VS Code API cannot write them, so other running tabs get them on their next start.
  - The managed settings are not put in the shared content and are not copied to other tabs while running. On each start, the app writes that tab's values (the wrapper path differs between Windows and WSL).
  - `claudeCode.preferredLocation`, which the helper extension writes for a moment when bringing a conversation to the front and when opening the first conversation of a new worktree ([below](#helper-extension)), is also copied to the other tabs and is soon set back.
- Tabs stopped by suspend, restart, or exit also have their last changes taken in. The app does not write to stopped tabs; they get the shared content on their next start (when a worktree is removed, its folder is removed too).
- When the shared content is first created (migration), the app collects `User/` from the tabs of that repository's worktrees (`git worktree list`). For the same key, it uses the value from the most recently updated file. For other files, it also uses the most recently updated one.
- A tab that joins the sharing for the first time after that (such as a tab that opened a folder inside a worktree) adds the settings and files the shared content does not have, and takes the shared content for the rest. Tabs that joined are recorded in `repo.json`.
- When a worktree is removed, the app removes that tab's `user-data-dir` but keeps the shared settings.
- For tabs of repositories in WSL, `User/` is inside WSL, so the agent reads, writes, and watches it.
- Not shared: `Machine/settings.json` (only the managed settings), `workspaceStorage/` and `History/` (per worktree), and `globalStorage/` (files extensions read and write while running; copying them between running tabs could corrupt them). Enabled and disabled extensions, panel layout, command history, and extension state (globalState) are kept by VS Code Web in the browser's IndexedDB per origin (port), so they are per tab ([limitations.md](limitations.md#vs-code-settings)).
- `claudeCode.hideOnboarding` is also per tab, excluded from migration and live settings sharing. Linked worktrees receive `true` at startup; primary's own preference stays intact. The resolved worktree root is compared with the resolved main worktree, so subfolders and tabs opened before primary follow the same rule.
- For linked tabs only, `src/agents/agent-onboarding.js` observes the Codex webview for the known first-run component's semantic message IDs and props, and calls its own `onAccept` callback. That callback saves onboarding completion through the extension and returns to chat. It also handles a first-run page reached with already-completed or delayed state ([upstream #25146](https://github.com/openai/codex/issues/25146)). Worktabs does not copy extension state, authentication, permissions, conversations, or layout. Unknown component shapes remain usable through the extension's original UI.

## Helper extension

[helper-extension/](../helper-extension/) adds desktop commands that VS Code Web lacks, and the mechanism for the app to bring a Claude conversation to the front. `npm run build:native` packs it as a VSIX, and the app installs it into the shared extensions folder at start.

- "Reveal in File Explorer" in the Explorer's right-click menu. code-server runs on the same machine, so it can open Windows File Explorer. The helper extension asks the app (`/explore` on the hook receiver), and the app opens it the way described in "File Explorer tabs" below. When the request cannot reach the app (a code-server started by hand, for example), the extension opens a new window with `explorer.exe /select`.
  - On macOS it is "Reveal in Finder". The display name is set in `package.json`, so the extension has two commands with the same handler (`worktabs.revealInExplorer` and `worktabs.revealInFinder`) and picks one with `isMac` in the menu's `when`. In VS Code Web, `isMac` depends on the OS of the browser (the app's window), so WSL tabs (Windows) keep File Explorer.
- Bringing a conversation to the front: the helper extension listens on a random port on `127.0.0.1` and reports that port and its own token to the hook receiver (the app passes the hook URL and token in code-server's environment variables).
  - The helper extension brings a conversation to the front the same way the Claude Code extension does when you open a row in its conversation list (Session history). It calls `claude-vscode.editor.open <session_id>` with `{ programmatic: 'honor-preferred-location' }` as the sixth argument.
    - If the conversation is in an editor tab, the extension brings that tab to the front.
    - Otherwise, if `claudeCode.preferredLocation` is `sidebar`, the extension shows the conversation in the right panel (side bar). If the right panel already holds the conversation (behind the one in front), it switches to it without starting a new claude. If not, it opens it from history.
    - If `preferredLocation` is `panel` (the default), it opens in a new editor tab. Even a conversation behind the right panel is opened in a second claude. So the helper extension sets the user setting `preferredLocation` to `sidebar` only for the call, and sets it back afterwards (two writes to the settings file). The extension reads the setting at the time the command is called, so this works. Calls that come one after another are handled one at a time.
    - When the workspace settings (`.vscode/settings.json`) set `preferredLocation`, that is a file in the repository, so the helper extension does not rewrite it and only shows the right panel.
  - Switching conversations inside a panel sends no hook, and no API lets other extensions read which conversation is shown where. The extension decides where to go, so the app does not need to know.
- Showing the chat panel for a new conversation: in a tab of a worktree added from the sidebar, the app calls `/new-conversation` once the helper extension has reported to the app. The helper extension uses the chat panel view's own focus command (`claudeVSCodeSidebarSecondary.focus`) to show the right chat panel and move focus to its input box.
  - It does not use `claude-vscode.editor.open` or `claude-vscode.sidebar.open` as they are. The former opens the conversation in an editor tab, and both rewrite the Claude Code extension's `claudeCode.preferredLocation` (where new conversations open).
  - When you wrote an issue, PR, or task in the add dialog, the app passes that instruction (`prompt`) to `/new-conversation`. The helper extension calls `claude-vscode.editor.open` with the same arguments as the Claude Code extension's "new conversation tab" (conversation, instruction, column, group, whether full screen, `{ programmatic: 'honor-preferred-location' }`). Called this way, the extension opens a new conversation at the `claudeCode.preferredLocation` location and puts the instruction into the input box (without sending it), and does not rewrite the setting. This is not a public interface (it is how the extension calls itself), so check it when the extension version goes up.
  - If `preferredLocation` is `panel` (the default), it opens in a new editor tab. The extension rewrites the setting to `panel` when you open a conversation in an editor tab, so this is the common case. So, as when bringing a conversation to the front, the helper extension sets the user setting `preferredLocation` to `sidebar` only for the call and sets it back afterwards (with the same queue). The extension shows the right chat panel (`claudeVSCodeSidebarSecondary.focus`) and opens the conversation there. Even if the right side bar shows the built-in chat, it switches to the Claude Code chat panel.
  - The right chat panel creates a conversation of its own and starts claude the first time it appears. The conversation with the instruction opens as a separate new conversation, so an empty conversation stays behind it and one extra claude runs. The same happens if the chat panel is shown before the call, and the extension has no way to stop this. The empty conversation was never started, so it has no row in the sidebar ([limitations.md](limitations.md#claude-code-extension)).
  - When the workspace settings (`.vscode/settings.json`) set `preferredLocation`, that is a file in the repository, so the helper extension does not rewrite it and calls the command as is (it opens at that location).
- Showing the Claude Code chat panel in the right side bar: VS Code 1.139 shows the right side bar (secondary side bar) by default (the default of `workbench.secondarySideBar.defaultVisibility` is `visibleInWorkspace`) and first shows the built-in chat (`workbench.panel.chat`). The AI features are off ([above](#code-server)), so it is empty. The Claude Code chat panel only shows an icon at the top, and the extension does not build the chat panel's page until it is shown. The conversation you had in the chat panel before does not come back either, and its claude does not run, so the sidebar has no row for it. VS Code Web remembers which view was shown per origin (port), so this happens in tabs opened for the first time (a new worktree, for example) and in tabs whose port changed.
  - So when the helper extension reports in, the app checks in the tab's page what the right side bar shows (`src/conversations/secondary-sidebar.js`). For each view container opened in the right side bar, VS Code creates an element (`.composite`) carrying its id and hides all but the one shown. The extension API cannot tell which view is shown.
  - If the built-in chat is shown, the app calls `/show-chat` on the helper extension. The helper extension calls the open command VS Code registers for each view (`claudeVSCodeSidebarSecondary.open`) with `{ preserveFocus: true }`. Focus stays in the editor, the side bar switches to the Claude Code chat panel, and the extension builds the chat panel's page. The conversation you had in the chat panel before comes back too. In VS Code without a right side bar, it calls `claudeVSCodeSidebar.open`.
  - This command opens the right side bar even when it is closed. So when the right side bar is closed, or shows another view (including Claude Code), the app does nothing. A right side bar you closed yourself does not open each time you open the tab.
  - The helper extension reports in (`onStartupFinished`) after VS Code restores the views (on the development machine, 3 to 4 seconds after the built-in chat appears). If the app still cannot tell (the view elements do not exist yet), it checks again every 0.5 seconds for up to 5 seconds.
  - In a tab of a worktree added from the sidebar, `/new-conversation` opens a conversation, so the app does not call this as well.
  - In both cases, after the chat panel is shown, the app sets its width ([below](#width-of-the-right-chat-panel)).
- Writing settings: the app passes settings changed in other tabs of the same repository through `/settings`. The helper extension writes each key with `WorkspaceConfiguration.update` (user settings) and returns the keys it could not write ([above](#sharing-vs-code-settings)).
- Passing the theme colors to the sidebar and dialogs: VS Code writes every theme color as a CSS variable (such as `--vscode-sideBar-background`) on `.monaco-workbench` in the page, and adds the theme kind (`vs`, `vs-dark`, `hc-black`, `hc-light`) as a class. The app reads these from the tab's page (`src/window/theme.js`). It reads them when the helper extension reports to the app (when VS Code starts) and when the helper extension reports a theme change (`onDidChangeActiveColorTheme`, `/theme` on the hook receiver). The VS Code extension API cannot read the theme color values themselves.

## Width of the right chat panel

On a new port, VS Code shows the right side bar at 300 pixels. That is narrow for chat, so in a tab opened for the first time, the app sets the width of the chat panel (`src/conversations/secondary-sidebar.js`).

- The app sets it when it replaces the built-in chat with the Claude Code chat panel (`/show-chat`), and after calling `/new-conversation` in a tab of a worktree added from the sidebar ([above](#helper-extension)). Both are tabs opened for the first time on that port.
  - After that, VS Code remembers the width per port, so the app does not touch it from the second time on. A width you changed yourself, a closed right side bar, and a right side bar showing another view all stay as they are. Changing the primary's width later does not change the width of worktrees that have already been opened.
  - When you resize the window after opening, VS Code handles it.
  - Repositories in WSL work the same way.
- The widths are:

  | Tab | Width |
  | --- | --- |
  | A worktree other than the primary | The same width as the chat panel of the same repository's primary |
  | The primary (when it is new again, for example because its port changed) | The width of that primary the app remembers |
  | The primary opened for the first time, a worktree whose primary width is unknown, a folder that is not a git repository | One third of the combined width of the editor area and the chat panel (editor area : chat panel = 2:1) |

  - The combined width of the editor area and the chat panel, when the panel is at the bottom, is the width without the activity bar and the side bar on the left.
  - No width is narrower than 300 pixels (the VS Code default), and 400 pixels are left for the editor area. If the window is narrower than when the primary's width was read, the editor area would otherwise get too narrow. In a window too narrow to meet both, the app uses 2:1.
- The extension API has no way to change the side bar width. So the app simulates dragging the sash between the editor area and the right side bar in the tab's page. It sends `mousedown` to the sash and `mousemove` and `mouseup` to the window (with these, the sash in VS Code 1.139 starts and follows a drag). VS Code remembers this width just like a width you dragged yourself.
  - They are script events, so focus does not move. It stays in the editor.
  - This depends on the structure of the VS Code page (`.part.auxiliarybar`, `.part.editor`, `.monaco-sash`) and the events the sash accepts, so check it when the code-server version goes up.
  - Other options were not taken. `workbench.action.increaseViewWidth` changes the width only by a fixed amount and needs focus in the right side bar. Writing the width VS Code remembers (`workbench.auxiliaryBar.size`) in advance would mean writing to the per-port IndexedDB before the page loads.
- The primary's width is remembered in pixels. VS Code also keeps the right side bar width in pixels and does not change it when the window is resized.
  - The width VS Code remembers is per port, so it cannot be read unless the primary's tab is running. So when the primary's tab is closed or suspended, or the app exits, the app reads the width of the right side bar (`.part.auxiliarybar`) from the tab's page and remembers it per repository (`chatWidths` in `tabs.json`, up to the 200 most recently read repositories). It also remembers the width it set when opening the primary for the first time.
  - When a new worktree opens and the primary's tab is running, the app uses the width it reads then and updates the remembered width. If the tab is not running, it uses the remembered width.
  - It does not read from a primary whose right side bar is closed or maximized (no editor area shown). The width remembered before stays.
  - When reading, the app does not wait for a page that does not answer within 1 second, so that closing tabs and exiting the app are not held up.
- A primary that was opened before this feature existed and whose width was never changed opens at the VS Code default width. The app does not detect and fix the default width. Until you adjust that primary's width yourself, worktrees created from it also get 300 pixels.

## Dialogs

Electron's `dialog.showMessageBox` is a Windows task dialog. It follows neither the VS Code theme nor Windows dark mode and appears white (electron/electron#22231). So the app draws dialogs on a transparent page laid over the sidebar and tabs (`src/dialog/`).

- It is normally hidden and shown only while a dialog is open. While it is visible, you cannot click the tabs and sidebar below, and the app's keys (Ctrl+Alt+PageDown and so on) do not work.
- It is called with the same options as `showMessageBox` and returns the answer in the same form (`src/window/message-box.js`).
- The add worktree dialog uses the same page and the same queue (`src/dialog/add-worktree.js`). Checks while typing and the creation itself are requested from the page to the app, and the app performs them only for the repository of the add dialog in front.
  - An issue is read with `gh issue view --json number,title,state,url`. gh also answers for PR numbers, so if the URL contains `/pull/`, the app reads it again as a PR with `gh pr view --json number,title,state,url,headRefName,isCrossRepository,headRepositoryOwner`. For a PR URL, it reads with `gh pr view` from the start.
  - A PR is fetched before the worktree is created (`pullPlan` in `src/repos/worktrees.js`). For an open PR from the same repository, the app fetches `+refs/heads/<branch>:refs/remotes/origin/<branch>` and creates a branch that tracks it. For a PR from a fork, and for merged or closed PRs, it fetches `refs/pull/<number>/head:refs/heads/<branch name>` to create the branch directly, and sets `branch.<branch name>.remote` and `.merge` the same way as `gh pr checkout`. The description while typing is shown without fetching, so it appears at once.
  - The branch name is chosen by the configured `branchAgent` (`src/repos/task.js`). Claude uses `claude -p`: it replaces the system prompt and runs without tools, MCP, slash commands, user settings (`--setting-sources ""`), or session persistence. It runs in a temporary folder so that it does not read any project's agent guide. Codex uses `codex exec --sandbox read-only` in the repository, with the naming instructions in the prompt. Codex keeps control of its configuration and login.
  - Both providers use their active Worktabs extension's bundled executable (`src/agents/agent-cli.js`), without a separate CLI on PATH. Each suggestion reads `extensions.json` again instead of remembering a version folder. Codex's chat proxy shares the same binary selection. Codex selects `bin/<platform>-<architecture>/codex` (`codex.exe` on Windows); Claude uses `resources/native-binary/claude` (`claude.exe` on Windows) in its matching extension payload. Platform metadata and executable availability are checked before suggestions run.
  - WSL suggestions read the distribution's home and architecture, then its `~/.worktabs/extensions/extensions.json`. Only its Linux executable runs there, with its own environment and login. This also works before a code-server agent has started. Claude runs in `/tmp`, and Codex in the repository's Linux path. Missing files give extension setup instructions; authentication failures give sign-in instructions for that environment; other failures keep the execution error.
  - The prompt goes in the command's arguments, and standard input is closed so bundled CLIs do not wait for additional piped input. Usage-limit failures on standard output are shown even when standard error also contains a warning.
- The folder picker (`showOpenDialog`) and right-click menus are the Windows ones as they are. They follow the Windows light or dark setting, not the VS Code theme.

## UI language

The app's own UI (menus, dialogs, the sidebar, messages) is written in English in the code, as the argument of `t()` (`src/i18n/`). The Japanese is a table keyed by that English text (`src/i18n/ja.json`).

- The language is picked once, at start: the `locale` setting ([config.md](config.md)) if the app has that language, else English. An empty setting follows the system's preferred languages (Electron's `app.getPreferredSystemLanguages`).
- A string without a Japanese translation shows in English. When the English text of a string changes, its old translation is no longer used, and the string shows in English until it is translated again. `npm run translations` lists both.
- `{name}` in a string is filled in when it is shown. A translation keeps the same placeholders (a test checks this).
- Sentences are not built from parts, because the word order differs between the languages. Each sentence is one string, with placeholders for what changes. Where English needs a plural, the singular is a string of its own (`1 file …`, `{count} files …`).
- The pages (the sidebar and the dialogs) get the language and the table from the main process through their preloads, before their scripts run (`i18n:get`). `src/i18n/page.js` makes the page's `t()` from it, and fills in the text of the page's own HTML: an element with `data-i18n="English"` gets its translation as its text, and `data-i18n-title`, `data-i18n-aria-label`, and `data-i18n-placeholder` set those attributes.
- `src/sidebar/time.js` and `src/sidebar/checks.js` run both in the sidebar and in the main process or the tests. There they take `t()` from `src/i18n/`.
- The prompt a new worktree's first conversation starts with (`firstPrompt` in `src/repos/task.js`) is in the UI language too, so that Claude answers in it.

## Rebuilding the sidebar

The sidebar page keeps tree coordination, requests, press-held rendering, GitHub hover placement, and resizing in `src/sidebar/sidebar.js`. `src/sidebar/rows.js` builds repository, worktree, and conversation rows from injected state, selectors, DOM helpers, and action callbacks. Row rendering does not start data reads or own page interaction timers. The existing page scenarios and focused row tests share the same small DOM fixture.

The initial tab state and repository catalog load independently. Once a live tab update arrives, a delayed initial tab reply is ignored. This keeps restored or newly opened tabs in "Open repositories" and prevents closed tabs from reappearing while startup reads finish.

`src/sidebar/model.js` derives groups, section order, merged worktrees, filtered rows, and badges from an explicit state. It does not read the DOM or preferences. `src/sidebar/data.js` coordinates worktree, GitHub, and PR requests with injected host methods, clock, timers, and a changed callback. Its default timers call the browser functions without passing the controller as their receiver. A browser rejects that receiver, which would stop tree rendering and leave server badges, conversation states, and archived rows stale. Duplicate requests share their pending read. Superseded or invalidated replies cannot replace newer results. Worktree rows and PR results stay visible during loading and temporary failures; a successful empty read clears them. Pending CI is polled only for expanded groups. Refresh invalidates GitHub and PR reads; unloading the page disposes polling and ignores late replies. The renderer owns markup, preferences, menus, and pointer behavior.

The sidebar rebuilds every row and button of the list whenever something changes (`render` in `src/sidebar/sidebar.js`). A click goes to the common parent of the element pressed and the element released. If a row is rebuilt between press and release, the pressed row is no longer on the page, so the click does not reach the row.

- When the window comes to the front, the sidebar is rebuilt several times within 1 to 2 seconds: the app marks the front tab's conversations as seen, reads the tab's branch again, and reads the worktrees, PRs, and CI of expanded repositories again. If you press a sidebar row while another window is in front, that press brings the window to the front, so the click is easily lost. Rebuilds also happen when a Claude state changes and when CI is read again while it is running.
- Requests to rebuild come in bursts, so they are rebuilt at most once per animation frame, with the latest state (`src/sidebar/press.js`). The main process likewise sends its tab state to the sidebar at most once per turn of its event loop (`pushState` in `src/main.js`).
- So while a mouse button is held down on the sidebar page, rebuilds wait (`src/sidebar/press.js`). On release, after that click has been handled (in the next task), the sidebar is rebuilt once for everything that waited.
- The release does not always reach the page, so waiting also stops when the window loses focus and when a right-click menu appears (on macOS, the menu appears on press and receives the release). Waiting lasts at most 2 seconds.
- On macOS, a click on a window behind others only brings it to the front by default. To make the click also act on what you pressed, as on Windows, the window has `acceptFirstMouse`. It also applies to the VS Code in the tabs. Desktop VS Code works this way by default too (the `window.clickThroughInactive` setting).

## Sidebar width

The sidebar and each tab are separate `WebContentsView`s. When you drag the right edge and the mouse moves over a tab, mouse movement may stop reaching the sidebar page. So while dragging, the app stretches the sidebar view over the whole window (`startResize` in `src/window/window-layout.js`).

- The tab views are placed below the sidebar view. Normally they do not overlap, so nothing looks different. While dragging, the sidebar page receives the mouse wherever it goes.
- The sidebar page draws the sidebar at the dragged width and makes the rest transparent, so the tab below shows through. Before stretching, it fixes the sidebar at the current width, and releases that only after confirming the view is back. Otherwise the sidebar would flash across the whole window.
- While dragging, only the front tab is resized. Chromium sends mouse movement to the page at most once per frame, so resizing happens at most that often. VS Code redraws the same way as when the window is resized. Hidden tabs are resized all at once on release.
- If the view stayed stretched, the transparent page would take every click meant for the tabs. So the drag ends even if the page misses the release: on mouse movement with no button held, on loss of focus (a dialog appeared, you switched to another window, and so on), and when the sidebar page reloads or crashes.
- The dragged width is kept in `window.json`. The settings file is written by people, so it is not rewritten on every drag. The `sidebarWidth` setting is the default width; double-clicking returns to it.

## File Explorer tabs (Windows)

Windows has no API to add a tab to an existing File Explorer window. `claude-wrap.exe --explore` (`--explore-select` when selecting an item) opens one in this order.

- It finds the frontmost File Explorer window (`CabinetWClass`) and sends its tab area (`ShellTabWindowClass`) the same command as File Explorer's own "new tab" button (`WM_COMMAND 0xA21B`).
- It moves the new tab to the target folder through `Shell.Application`, selects the item if needed, and brings the window to the front. Windows lets a process started by the foreground process (app) bring other windows to the front. A process started by the extension host may not be allowed, so the app also starts the requests from the helper extension.
- If there is no window, or anything fails, it opens a new window with `explorer.exe`.
- It does not use the Windows setting "Open desktop folders and external folder links in new tab" (`OpenFolderInNewTab`). That is a Windows-wide setting, and this works with it left off.

## GitHub buttons

The URL is built from `git remote get-url` (origin, or the first remote if there is none) (`readRemote` in `src/repos/github.js`). These hosts are treated as GitHub:

- github.com, hosts starting with `github.` (GitHub Enterprise Server), and `<tenant>.ghe.com` (GitHub Enterprise Cloud with data residency)
- Hosts listed in the `githubHosts` setting ([config.md](config.md))
- Hosts gh is signed in to (`gh auth status --json hosts`; for older gh without `--json`, read from "Logged in to <host>" in `gh auth status`). Hosts registered in gh count as GitHub even if the token has expired

In addition, `gitlab.com` and hosts starting with `gitlab.` are treated as GitLab, and `bitbucket.org` and hosts starting with `bitbucket.` as Bitbucket. This is used for the icon on repository rows ([usage.md](usage.md#repositories)). Anything else is "other".

- For SSH URLs (`git@host:o/r`, `ssh://`), the host is first resolved to the real host name with the `hostname` from `ssh -G <host>`. People often switch accounts with an alias such as `Host github-work` (`HostName github.com`) in `~/.ssh/config`. `git remote get-url` applies `url.<base>.insteadOf` but not SSH aliases. `ssh -G` does not connect; it only prints the settings it would use.
  - ssh and gh run where the repository is (inside WSL for repositories in WSL). The app asks once per location and host, remembers the answer, and asks again on "Refresh the repository list" at the top. The remotes of every repository in the list are read, so asking per repository would be slow.
  - If ssh is missing or fails, the host name in the URL is used.
  - gh is asked only for hosts that neither the host name nor the settings identify (it is not asked even for hosts known to be GitLab or Bitbucket). `gh auth status` takes about 1 second to check the token.
- The port of an HTTPS URL stays in the page URL (`https://github.example.com:8443/o/r`). An SSH port is not a web port, so it is dropped.
- ssh.github.com, altssh.gitlab.com, and altssh.bitbucket.org (SSH on port 443) are treated as hosts of their services.

- The main process reads the repository row icons (GitHub, GitLab, Bitbucket, and so on) and visibility icons for every git repository in the list (`readVisibilities` in `src/main.js`), so they show even on collapsed rows.
  - Remotes are read only when a repository first appears in the list (up to 8 at a time; `readRemotes` in `src/repos/github.js`). "Refresh the repository list" at the top reads them all again. With hundreds of repositories, each read would call git hundreds of times (inside WSL for repositories in WSL).
  - The remotes read are sent to the sidebar before visibility is asked (`providers` in `repoMessage`). For rows of repositories known not to be on GitHub, the sidebar shows no GitHub button, whether collapsed or on hover. The add worktree dialog also uses this to decide whether its top field is only "What to do" ([worktrees.md](worktrees.md#adding)).
  - Visibility is asked with `gh api graphql` each time the list is read again (at start, on the refresh button, and after "Add repository…") (`repoVisibility` in `src/repos/github.js`). It is one call per place gh runs (gh inside WSL for repositories in WSL) and host, in batches of 100.
  - The query lists `repository(owner:, name:) { visibility url }` for each repository. Repositories that were renamed or moved to another owner still answer under the old name. `resource(url:)` returns `null` for these. `url` is the URL where GitHub keeps the repository now. If it differs from the remote URL, it is kept as `current` in `remotes` in `repos.json` and used to check whether a repository is cloned ("[Repositories not cloned](#repositories-not-cloned)" below).
  - If a repository is gone or not visible, the answer contains an error and gh exits with failure. gh still writes the answer to standard output, so the app reads the other repositories from it. An answer without `data` (not signed in, for example) is treated as a failure, and the previous results stay.
  - The provider, URL, and visibility are kept in `remotes` in `repos.json`, and on the next start those are shown first. What earlier versions kept in `github` was decided by host name only (and mistook SSH aliases), so it is not read.
- The main process also reads the PRs of your own that are approved but not merged (the red dot on the icon of a repository row) (`readApproved` in `src/main.js`, `approvedPulls` in `src/repos/github.js`), so they show even on collapsed rows.
  - The query is `viewer { pullRequests(states: OPEN, first: 100) }`. It reads the open PRs of the account gh is signed in to, in any repository. It is one call per place gh runs (gh inside WSL for repositories in WSL) and host, whatever the number of repositories. The PRs are not read from the worktree branches, because the worktree of a PR's branch may not be on this computer (made on another computer, or removed first).
  - The `repository.url` of each PR (the repository it would be merged into) is matched to the remote URLs, and to the current URL of renamed repositories (`current`), to find its repository (`repoKey`). They are sent to the sidebar as `approved` in `repoMessage`.
  - Whether a PR is approved is decided by `reviewDecision` (`isApproved`). On branches that do not require reviews, it is `null`. Then a PR is approved when `latestOpinionatedReviews(writersOnly: true)` (the latest review of each person who can write to the repository, the ones that count for GitHub's decision) has `APPROVED` and no `CHANGES_REQUESTED`. The search qualifier `review:approved` is not used, because it is not clear how it works in repositories that do not require reviews. Drafts and PRs in archived repositories are left out.
  - They are read after visibility is asked (once the current URLs of renamed repositories are known), every 5 minutes, when the window comes to the front (if 1 minute has passed since the last read), and 10 and 30 seconds after Claude pushes or merges (`startsChecks`). People approve PRs on GitHub, so nothing in the app tells when. The window stays in front all the time you work in its tabs, so they are also read every 5 minutes. One query costs about 1 point of the GraphQL limit (5000 an hour).
  - A place in WSL is read only while its distribution is running (`wsl.exe -l --running -q`, which does not start WSL), except after the list is read again. Reading every 5 minutes would otherwise keep starting a stopped WSL. Places not read, and places where gh failed, keep the previous result.
  - Hosts that gh is not signed in to (`gh auth status`) are not asked, and show no dot. This keeps the app from failing every 5 minutes where gh is missing.
  - They are not kept in `repos.json`. PRs merged in the meantime would show on the next start.
  - In an expanded repository, the sidebar drops a PR from the dot when its worktree row has read it (`branchPulls`) as merged, closed, or a draft (`approvedOf` in `src/sidebar/pulls.js`). Worktree rows read their PRs again as soon as something is done in the repository.
  - The dot is laid over the element that wraps the repository icon (`.provider-box`) with `position: absolute`, so the row does not get wider. It has `pointer-events: none`, so the GitHub buttons that come up on hover work the same. The icon has a hole around the dot (`mask-image`), because an edge in the background color around the dot would not match the background of a hovered row or of the icon. The wrapping element does not depend on the provider, so the same dot can show once MRs and PRs on GitLab and Bitbucket are read.

- The remote and default branch are read once, when a repository is first expanded. "Refresh the repository list" at the top of the sidebar reads them again.
- "This branch's PR" looks for a PR with `gh pr view <branch>`, and if none is found (or gh is missing), opens the PR creation page (`/compare/<branch>?expand=1`). If a PR exists, the creation page also links to it.
- The PR and CI of worktree rows are read with one `gh api graphql` call per repository (`branchPulls` in `src/repos/github.js`).
  - The query lists `pullRequests(headRefName: <branch>)` for each worktree branch. Listing a repository's PRs with `gh pr list` misses those older than the count limit (`--limit`). Naming the branch misses none, however many PRs there are.
  - The PR is chosen the same way as `gh pr view <branch>`. PRs from forks (`isCrossRepository`) are excluded; the open one is chosen, or else the newest.
  - For a branch created from a PR (one with `worktabs-pull` in the git config), that PR is also read with `resource(url: <PR URL>)`, and chosen if found. This also shows PRs from forks and PRs whose branch has a different name.
    - It is not read with `pullRequest(number: <number>)` because a number that does not exist in the repository (origin later changed to another repository, for example) makes the whole query fail (gh exits with failure too), and then no PR shows for the other branches either. `resource` returns `null` without an error even for a missing number.
    - If that PR is not found, the PR found by branch name is chosen, as for other branches.
  - The CI result is the commit's `statusCheckRollup`. `SUCCESS` is success, `FAILURE` and `ERROR` are failure, `PENDING` and `EXPECTED` are running. A commit's `statusCheckRollup` contains the workflows that ran on that commit, whatever the event (PR, branch push, tag push). So which commit is read decides which CI is shown.

    | Row | Commit read |
    | --- | --- |
    | Open PR | The PR's last commit (`commits(last: 1)`) |
    | Merged PR | The PR's `mergeCommit` (CI of the push to main) |
    | No PR (including the default branch and a HEAD with no branch) | The worktree's HEAD (`HEAD` from `git worktree list`) via `object(oid:)` |

  - The HEADs of all worktrees go into the same query (`h0`, `h1`, ...), since whether a PR exists is unknown until the answer is read. A commit not on GitHub (not pushed) returns `null` without an error.
  - The name, result, and time of each check are read from `statusCheckRollup.contexts`, up to 30 (the same items as `gh pr checks`). GitHub Actions jobs are shown as "workflow name / job name".
  - For the HEAD commit, only checks for a push to that row's branch are kept, by the check suite's `branch` (`refs/heads/main`, `refs/tags/v0.2.0`) (`ownChecks` in `src/sidebar/checks.js`). Tag checks are kept only on the default branch's row. Success, failure, and running are summarized again from what is kept. A branch just created from main has the same HEAD commit as main, so without this, main's CI would show.
  - CI for the merge commit and the HEAD commit shows for 1 hour after success, and 1 day for failure or running, counted from when the last check started or finished (`recentChecks`). The time of the checks is used instead of the time since the merge or pull so that releases tagged later on an old commit, and re-runs, also show. The decision is made when the sidebar draws, so it disappears as time passes (on the next redraw) without reading again.
  - One query costs about 1 to 3 of the GraphQL limit (5000 per hour) (3 with 10 worktrees). So that it is not read every time the window comes to the front, it is not read again within 15 seconds of the previous read. When Claude finishes its work (it may have created a PR), it is read at once. While shown CI is running, it is read every minute.
  - When Claude pushes or similar (when `tool_input.command` of a PostToolUse hook is `git push`, `gh pr create`, `gh pr merge`, `gh release create`, and so on; `startsChecks` in `src/repos/github.js`), it is also read 10 and 30 seconds later. Right after a push, GitHub may not have created the check suites yet, and `statusCheckRollup` may be empty.
  - gh runs where the repository is (gh inside WSL for repositories in WSL).
  - The PR's last commit (`headRefOid`) is also read. If the PR is merged and that commit equals the worktree's HEAD (`mergedAtHead` in `src/repos/github.js`), every commit of the branch is in the merged PR. The row's trash button then always shows, and the remove confirmation turns on deleting the branch by default ([worktrees.md](worktrees.md#removing)).
- The worktree remove confirmation reads only that branch's PR again with the same query (`removalPull` in `src/repos/worktree-removal.js`). The row's PR may be stale, and removal from a tab's right-click menu does not go through the sidebar. It waits up to 5 seconds; after that it stops gh and shows the confirmation without a PR. The worktree folder may be gone, so gh runs in the repository's (primary's) location.

## Repositories not cloned

"Repositories not cloned" in the sidebar ([usage.md](usage.md#repositories-not-cloned)) is your account's repositories as reported by gh, minus the repositories in the list. The matching and the choice of clone destination are in `src/repos/clone.js` (testable without Electron), and the gh query is `ownedRepos` in `src/repos/github.js`.

- How they are read: for each host gh is signed in to (`gh auth status`, including GitHub Enterprise), the app calls `gh api --hostname <host> --paginate 'user/repos?affiliation=owner,organization_member&per_page=100'` once.
  - One call returns the repositories you own (including your forks) and the repositories of organizations you belong to. Other people's repositories where you are only a collaborator are not included.
  - `gh repo list` is not used. It would need one call per owner, and it has no `--hostname` (the host is switched with the `GH_HOST` environment variable). With `gh api`, `--hostname` reaches GitHub Enterprise too, as with the visibility query. gh decides the REST path for GitHub Enterprise Server (`/api/v3`).
  - `--jq` makes gh print only the owner (`login`, and whether it is a `User` or an `Organization`), name, `html_url`, whether it is a fork, whether it is archived, visibility, description, and last push, one line each (`readOwnedRepos`). Archived ones are dropped. The owner and name go into command lines and paths, so only those made of letters, digits, `.`, `_`, and `-` (not starting with `-`, and not `.` or `..`) are accepted.
  - gh is the Windows or macOS gh (gh inside WSL is not asked). If gh is missing or not signed in, nothing is shown. For hosts that could not be asked, the previous results stay (`mergeOwned`).
- When they are read: each time the list is read again, together with remotes and visibility (`readVisibilities` in `src/main.js`). The gh query starts when reading the remotes starts, but its result is taken in only after the remotes and visibility (current URLs) are read. This keeps cloned repositories from showing as not cloned on the first start. The result is kept in `owned` in `repos.json`, and on the next start that is shown first.
- Matching (`unclonedGroups`): each time the list is sent to the sidebar, the following are removed from `owned`. All are compared as `<host>/<owner>/<name>` in lowercase (without the port).
  - The remote URLs of the git repositories in the list (both Windows and WSL), and the current URL GitHub answered (`current`). Repositories renamed or moved to another owner match on the current URL even if the remote URL is still the old one.
  - The last three names of the folders of the repositories in the list and of the repositories of open tabs. Folders in the ghq layout (`.../<host>/<owner>/<name>`) match this way even when the remote could not be read (WSL does not respond, for example) or has not been read yet (just cloned outside the app).
  - Owners in `hiddenGithubOwners` are also removed here.
- Order: grouped by owner, with your account first (github.com first), then organizations (by name). Within an owner, by last push.
- Cloning (`startClone`):
  - The destination candidates are here (Windows or macOS) and, on Windows, the WSL distros. The distros are those read through `repoSources` that either have repositories in the list or have ghq installed (when reading the list, the app marks whether `ghq` exists; `ghq` in `repoCatalog`).
  - If ghq is available (`ghq root` runs), the app runs `ghq get [-p] <host>/<owner>/<name>` and finds the cloned folder from `ghq list --full-path`. With `ghq.<url>.root`, a repository may go into a root other than `ghq root`.
  - Without ghq, the app asks with the clone destination dialog (`src/dialog/clone.js`) and runs `git clone -- <URL> <folder>`. git runs where the folder is (inside that distro for a WSL folder).
  - Whether to use https or SSH is decided by `gh config get git_protocol -h <host>` (`gitProtocol`; https if gh is missing). This is the same as `gh repo clone`.
  - It runs with `GIT_TERMINAL_PROMPT=0`. If git asks for a user name where there is no terminal, it waits until the timeout (10 minutes). Git Credential Manager asks in its own window. Inside WSL, environment variables are not passed, so the command runs as `env GIT_TERMINAL_PROMPT=0 <command>` (`env` in `runAt`).
  - When it finishes, the app adds the folder to the list and puts its remote URL into `remotes` as known (`addClonedRepo`). The row then leaves "Repositories not cloned" without waiting for the list to be read again.
- Candidates in the clone destination dialog (`cloneRoots`): derived from the repositories in the list at the destination (Windows or that distro).
  - If the last three names of a folder equal the remote's `<host>/<owner>/<name>`, it is treated as the ghq layout and `<root>` becomes a candidate (clone in the same layout). If the remote is not on GitHub or has not been read, this is decided by whether the name three levels up looks like a host name (contains `.`).
  - Otherwise, the parent folder becomes a candidate (clone into `<parent>/<name>`).
  - Candidates are ordered by how many repositories they hold. If the last clone destination (`cloneRoot`) is at the same location, it is put into the field first. A folder chosen with "Browse…" and `cloneRoot` use the layout of the matching candidate if there is one; otherwise they use the ghq layout only when a host folder (such as `github.com`) exists below them.

## The claude wrapper

`claudeCode.claudeProcessWrapper` is set to a program that wraps claude. Each OS has its own, but the command line is the same and they pass the same tests (`test/wrap-fixture.js`).

| OS | Wrapper |
|---|---|
| Windows | `native/claude-wrap.exe` (`native/ClaudeWrap.cs` built with the csc.exe that comes with Windows) |
| macOS | `<data folder>/bin/claude-wrap` (an sh script that calls `src/agents/mac-claude-wrap.js`) |
| WSL | `~/.worktabs/bin/claude-wrap` (`src/wsl/wsl-claude-wrap.sh`; does not pick up usage) |

- The macOS wrapper is started by the extension as an executable. No node it can rely on is in PATH, so the app writes these two files to the data folder on each start. They keep up even if paths change (the app is moved).
  - `mac-claude-wrap.js`: the wrapper itself. In the packaged app it is inside the asar, which plain node cannot read, so it is copied out.
  - `claude-wrap`: an sh script that runs it with the app's own binary (`ELECTRON_RUN_AS_NODE=1`). code-server's node would also work, but it is not ready yet when the hook settings are written. The variable is limited to the wrapper and not passed to claude.
- Only the Windows wrapper has `--explore` ("File Explorer tabs" above). On other OSes, the app leaves it to the shell.

## hooks

- When the extension starts claude, this wrapper adds `--settings <hook-settings.json>`. The hooks apply only to sessions the app manages; neither `~/.claude/settings.json` nor the repository's `.claude/` is changed.
  - The extension also runs claude's subcommands through the wrapper, such as `claude auth status --json` to check the sign-in. claude rejects `--settings` after a subcommand, and a subcommand starts no session, so the wrapper adds it only when claude's first argument is an option (or there is none).
- SessionStart alone cannot be an http hook, so `claude-wrap --hook` forwards it.
- The wrapper passes its own process ID to claude as `WORKTABS_PROC_ID`, and the hooks add it as a header (`X-Wrapper-Proc`). The extension starts one claude per conversation opened in a panel (even within one panel, each conversation has its own claude), so this tells apart the conversations of each panel.
- The receiver listens on a random port on `127.0.0.1` and checks a token generated per start.

## Usage

The extension starts claude with stream-json. In that output, claude writes the usage read from response headers as a `rate_limit_event` (`five_hour` and `seven_day` in `rate_limit_info.unifiedWindows`). The extension also uses this to show usage in its panel.

- The wrapper receives claude's standard output through a pipe and passes it on to the extension at once, unchanged. It also sends only the `rate_limit_event` lines to the hook receiver (`/usage`). Standard input and standard error are inherited by claude as before.
- claude's statusLine command is called only in the terminal UI, so it cannot be used with the extension's claude. The undocumented OAuth API (for fetching usage) is not used either.
- The received values are also written to `hooks.log`.

Codex quota also uses the same extension-owned app-server proxy as conversation state. The proxy observes the supported [`account/rateLimits/read` and `account/rateLimits/updated` protocol](https://learn.chatgpt.com/docs/app-server) without making requests itself.

`src/agents/usage-polling.js` schedules quota reads after startup extension setup, every 5 minutes, and after Codex account events. It allows one read per provider and coalesces overlapping requests into one pending retry. Failed reads do not stop the schedule. Quit cancels reads and clears pending retries. The scheduler and tracker replay run without Electron so tests can exercise account changes and overlapping reads.

`src/agents/usage-refresh.js` resolves the active host extension's binary each time; WSL-only accounts are not polled. The 20-second deadline covers binary resolution and the entire helper connection. Late resolution after cancellation or timeout cannot launch a helper. Codex initializes its own short-lived app-server, reads account identity and then subscription limits. An `account/updated` notification invalidates pending responses, so the reader issues new identity and quota requests with new IDs inside the original deadline. A newer quota notification also triggers a new full read when it supersedes the pending response. Missing subscription identity fails visibly instead of reading an anonymous quota. Claude sends only stream-json `initialize` and experimental `get_usage` control requests with `skip_behaviors`; hooks, tools, MCP, slash commands, project settings and session persistence are disabled. Neither helper sends a user message or starts a model turn. Responses are strictly projected; diagnostic output and full account/usage responses are discarded. Unsupported Claude versions fail visibly and retry later. Complete Claude reads replace missing windows; reads begun before a newer live event cannot overwrite it. Enabled provider sections remain visible when values reset, expire or fail to load.

Codex replay checks each account and quota event's acceptance. A protocol response alone is not a successful display refresh: a quota must be accepted and supply a current known window. Empty or unknown snapshots remain unavailable. Each accepted live account event advances an in-memory epoch; a background read begun before that event is rejected before replay, including events with equal timestamps. The live account notification queues a fresh attempt. This keeps a delayed host read from reviving a previous account or undoing a newer identity check. Rejected snapshots and failed reads do not extend the old snapshot's receipt time.

The footer shows an active background read separately from stale quota data. Failures, timeouts and rejected refreshes remain visible beside old windows. Provider and row tooltips include the last quota receipt, last refresh attempt and next scheduled attempt. `logs/usage-refresh.log` records only provider, timing, outcome, fixed failure/rejection categories, acceptance counts, last quota receipt and next scheduled time. CLI errors and stderr are never copied into it. No account emails, identity hashes, tokens, full responses or quota payloads are logged. Diagnostic write failures cannot stop polling.

- `src/codex/codex-quota.js` projects only primary/secondary percentages, reported window durations, reset timestamps, and optional bucket IDs/names. A multi-bucket read takes precedence over its backward-compatible single-bucket view. Credits and reset-credit details are discarded.
- The proxy remembers quota request order and observes account changes. An older read response cannot replace a newer notification or read. Pending reads from before a login, logout, or account update cannot supply the new account's quota.
- Account observation emits only auth mode and a hash of the documented account email for in-memory identity comparison. It does not inspect token fields or forward emails, login parameters, full authentication responses, or auth URLs.
- Sanitized account and quota events use the token-protected `/codex` endpoint, including WSL's existing forwarding path. The queue preserves account boundaries and bucket updates. These events do not create conversation rows or write to `hooks.log`.
- `src/codex/codex-usage.js` keeps account-wide snapshots in memory, separate from Claude's `UsageTracker`. It compares observation times across tabs, never sums percentages, replaces the bucket list on full reads, and updates only the reported buckets on notifications. Routine account notifications keep the displayed snapshot while fencing incoming quota until identity is rechecked. Matching identity preserves the snapshot until new quota arrives; a different identity, login, logout or non-subscription mode clears it. Failed reads emit no empty snapshot and do not renew its freshness.
- The latest observed account owns the footer. A matching known account identity can report from several tabs. Without a reported identity, only eligible snapshots after the last account boundary can contribute. This conservative display is not a multi-account dashboard.
- Missing fields, reset expiry, and snapshots older than 15 minutes produce unknown percentages. A timer refreshes expiry, stale states, and time labels each minute. The footer labels both providers and uses **used** percentages for both; Codex's `usedPercent` needs no inversion.

## Conversation state

`src/conversations/conversation-store.js` owns conversation state, provider-specific process ownership, ordering, unread and archive marks, and navigation metadata. It has an injected clock and performs no file reads, process probes, or timer work. `src/conversations/claude-observer.js` attaches transcript observation and local process polling explicitly, with injected readers, liveness checks, and timers. It keeps byte offsets and partial-line buffers outside the store, reads a bounded tail on first attachment, and ignores old interruption markers when a turn starts. Complete title records and observed transitions update the store. A temporarily unreadable transcript is retried without advancing its offset. Start and stop are idempotent; quitting stops observation. WSL process exits still arrive through the distribution agent. `HookServer` remains the authenticated HTTP bridge in `src/conversations/hooks.js`; its `SessionTracker` export is a compatibility adapter that combines the store and observer.

The app keeps a state per `session_id` and shows the most urgent one on the tab.

Claude Code uses the hooks described above. Codex uses the same `ConversationStore` for badges, elapsed time, counters, unread results, archiving, and stop warnings. Its adapter observes the app-server owned by the Codex extension, rather than starting a separate agent that cannot see that extension's conversations.

### Codex app-server

`src/conversations/conversation-navigation.js` confirms a Codex reveal from the mounted, visible local thread context, even when permission controls are disabled for a busy thread. A successful URI dispatch is only a request; it does not clear unread until the requested thread is confirmed. Blank, ambiguous, unsupported, or stuck renderers reach a 15-second deadline and get the navigation warning. Tab/run changes and newer reveals invalidate late results.

New-worktree tasks use `src/conversations/first-conversation.js`. The helper activates Codex and acknowledges `chatgpt.newChat`; it makes no model request. After that, a bounded probe checks the mounted permission context for a local new conversation and a single visible, empty rich-text input. Native `insertText` adds the editable draft without pressing Enter or invoking a submit callback. Unknown shapes, existing drafts or threads, rejected input, and startup failures show the task in a copy-task recovery dialog. Claude keeps its extension command's prefill argument.

- Before starting code-server, the app sets the instance's managed `chatgpt.cliExecutable` to a proxy (`src/codex/codex-launch.js`, `src/codex/codex-wrap.js`). The real CLI is the binary shipped with the active `OpenAI.chatgpt` extension. Chat and branch suggestions share binary selection in `src/agents/agent-cli.js`. Branch suggestions run the binary directly, without posting chat conversation events. Installing, updating, re-importing, and restoring the extension also determines the CLI version; Worktabs does not maintain a second CLI installation.
- On Windows, `native/CodexWrap.cs` launches the proxy with code-server's node. A job object stops node, app-server, and their children when the extension kills the launcher. On macOS and WSL, an executable shell script runs the proxy with code-server's node.
- The proxy forwards arguments, stdin, stdout, stderr, and the exit code. It observes both sides of the newline-delimited JSON protocol. It makes no app-server requests and sends no approval decisions. Authentication and approvals stay with the Codex extension.
- `src/codex/codex-events.js` maps `thread/*`, `turn/*`, and `item/*` events to state. A turn starts `working`, finishes `done`, fails `error`, and becomes `idle` when interrupted. Runtime `idle` after completion keeps the result visible. A runtime status it does not know counts as `working`, so a newer extension cannot make a busy thread look idle. Tool failures and errors that will retry do not end a turn.
- When the app-server answers the extension's `initialize`, the proxy sends `codex-observer` once. The tab then counts as observed until code-server restarts. Before an update, a tab whose Codex extension is active (the helper's `/codex-active`) but is not observed must be closed, because the extension may have started its CLI without the proxy. Other tabs wait only for working and waiting conversations and unsaved edits, as Claude tabs do.
- Command, file, permission, user-input, and MCP elicitation requests make the conversation `waiting`. Each request stays pending until resolved (or its item completes). Other item events cannot clear a concurrent approval. A turn ending clears its pending requests, and events from an older turn cannot finish a newer one.
- Only conversation metadata and sanitized quota/account state are sent to the token-protected `/codex` endpoint, in order and independently of the protocol pipes. Full auth responses, credentials, streamed output, and listed history are not sent. WSL forwards the endpoint through its agent and converts the working folder to a Windows path.
- A process holds several threads at once. Loading another thread does not remove the previous row; ending the process releases its ownership but keeps used threads as idle history rows. A thread held by another process keeps its state. The same thread opened in different Worktabs tabs has separate state, and Codex IDs cannot collide with Claude session IDs.
- New empty threads have no row until used. Resumed threads get an idle row. Titles come from the thread name. The last user-message item in loaded turns takes precedence over the thread preview, which can describe the first prompt. An old resume snapshot cannot replace a live turn or prompt.
- Delegated children are identified by `parentThreadId`, the structured `subAgent.thread_spawn` source, a completed spawn/wait collaboration item, or a `subAgentActivity` item of kind `started` in the parent's turn (newer servers report spawns this way, and the child's own events carry no source). Other activity kinds only update a known child, since they can target an ancestor. Their parent ID, nickname, role, and agent path travel through the observer and store and are saved with navigation metadata. The sidebar labels them as subagents and nests each under its parent; a click still opens the child's own thread. They contribute working/waiting badges and stop warnings, but do not create separate completion unread marks or completion notifications. Internal guardian, review, and compaction threads remain excluded.
- A collaboration item's `agentsStates` can reconcile a child's missing completion. The tool's own status is not the child's status: a completed spawn or timed-out wait can leave its target running. Target turn IDs captured at the tool's start protect newer child turns from old wait results. Running target snapshots cannot clear pending approvals or revive completed children. A delayed active thread status also cannot revive a terminal turn without `turn/started`. No idle timeout or prompt-text matching guesses that a turn has finished.
- Internal title and description generation threads are excluded by their `threadSource` (`thread_title` or `thread_description`), including the source on a client start/fork request. Notifications for unknown threads wait for pending start/fork responses so they cannot briefly create an internal row. Excluded IDs stay excluded after close and late events. These threads do not affect counters, unread results, notifications, or stop warnings. Account and quota observation continues independently. A user-created temporary thread still appears live, but is not saved in Worktabs history.
- `tabs.json` stores each open tab's Codex navigation metadata: provider, thread and turn IDs, title, last prompt, cwd, and the Worktabs archive mark. It stores no process IDs, live state, unread result, or authentication data. Writes from conversation changes are coalesced and flushed on quit. Restored rows are idle; they do not start another app-server or resume a thread until clicked or opened by the extension.
- Clicking a Codex row activates the extension and opens `<vscode.env.uriScheme>://openai.chatgpt/local/<thread-id>` through the workbench opener. The extension's URI handler focuses its chat sidebar and navigates to that thread. No conversation editor is created. The provider belongs to the conversation, even when the tab's default agent is different. A click before the helper registers is kept until registration; switching tabs cancels that pending navigation. Failed dispatch or a rejected `thread/resume` shows an explicit warning and tries the Codex sidebar.
- Worktabs archiving only hides a row. It does not issue `thread/archive`; the persisted Codex log is untouched. Observed `thread/archived` and `thread/deleted` events remove saved rows, while `thread/closed` only releases ownership. The observer makes no `thread/list`, `thread/resume`, or `thread/fork` requests of its own.

The wire events are described in the [official OpenAI app-server documentation](https://learn.chatgpt.com/docs/app-server). The CLI override and sidebar URI handler are extension integration points; check both after an extension update.

### Claude Code hooks

- For each conversation, the app records the claude process running it. When the same claude moves to another conversation, the previous conversation is dropped, and when the process ends (the panel is closed), the conversation is treated as ended. SessionEnd often does not come, and the same conversation may be open in two panels.
- The extension starts claude as soon as a panel opens (sometimes a claude that ends right away). So only conversations where a prompt was sent, and conversations resumed from history, get a conversation row.
- The conversation title is read from `custom-title` (when renamed) or `ai-title` in the transcript (JSONL).
- When you move to another conversation inside a panel, the extension does not stop the previous conversation's claude (it stops it when the panel is closed, reloaded, and so on). So conversations moved to the back also keep their rows. Conversations archived in the sidebar are marked and shown neither as rows nor in tab badges. The mark is kept only in memory (a row exists only while its claude runs), and it is removed when the conversation becomes working or waiting for approval. Archiving in the extension's conversation list lives inside the extension (`globalState`), which neither other extensions nor the app can access, so it is not synced.
- Declining a permission with "No" or interrupting by reloading sends no hook. So the app watches for the interruption records left in the transcript and resets the state.
- For each conversation, the app records when it entered its current state (only when the state changes; a hook with the same state does not change it). The sidebar shows the elapsed time from this and the current time, and advances only the text every 10 seconds without rebuilding the rows. The time format is in `src/sidebar/time.js`, used by both the page and the tests.

## Webview compatibility probes

`src/conversations/webview-react.js` shares the private React discovery used by conversation visibility, Codex approvals, and linked-worktree onboarding. It follows a DOM node's `__reactFiber$` attachment to the root, then searches `stateNode.current` for that exact node. The attachment's alternate props are never used as current state. Detached nodes, missing roots, unmounted nodes, cycles, and traversal limits produce explicit unavailable results. Ancestor discovery is limited to 512 levels and 10,000 nodes. In the official Codex extension 26.1007.21434, the introductory heading has 134 ancestors and a resumed thread’s permission control has 257. The former 100-level bound rejected these valid mounted controls. React element props are also bounded; feature probes keep their own semantic IDs, capability checks, callbacks, and fallbacks. The same helpers are serialized into injected scripts without Node dependencies.

These are internal extension shapes, not a public API. Each read discovers the current tree again so history switches and replaced buttons do not reuse stale props. Unknown shapes retain unread results, leave Codex's approval mode intact, and keep the onboarding UI available. Only exact conversation IDs clear unread. The approval watcher preserves trusted user choices and confirms a selection on a later snapshot. Onboarding remains limited to linked worktrees and calls the walkthrough's own completion callback. Reinjection disposes the previous watcher; disposed watchers ignore late asynchronous results.

## Codex approval preference

- `codexApprovalMode` in the Worktabs config is independent of Claude's `permissionMode`. Settings save `auto-review` or `manual`; the default is automatic review when available.
- At an `openai.chatgpt` webview's frame load, `src/main.js` installs the observer from `src/codex/codex-approval.js`. It reads the React permission picker's rendered element props, rather than localized labels or an extension version. The legacy callback shape and the profile-selection shape were inspected in extension 26.1007.21434. The picker resolves account feature availability, app-server capabilities, config, and managed requirements before exposing enabled options.
- The observer selects only an enabled option through the extension's own guarded callback. That callback updates the remembered selection and the permission overrides together. Worktabs sends no app-server fields, reviewer enum values, approval responses, or extra user turns. It does not write `config.toml`, alter the CLI proxy, or access other applications' extension storage.
- Only a known, empty composer on the local extension host is eligible. Existing threads, remote hosts, Full Access, and custom profiles retain their selections. A trusted pointer or keyboard interaction stops initial setup. A successful selection is confirmed from the picker before being reported as effective.
- A frame's observer tracks composer transitions and applies the preference once per new composer. Settings changes update the preference for its next composer. Loading is retried for at most 10 seconds; an unavailable option, unknown picker, restriction, or selection failure ends that attempt. No startup retry loop is introduced. A new frame re-evaluates its active extension after updates, restores, or code-server restarts, separately in each Windows, macOS, and WSL tab.
- The extension's permission control remains the source of the effective mode. Diagnostic state in the webview's `worktabsCodexApproval.result` distinguishes loading, unavailable/restricted options, unknown picker shapes, explicit choices, existing conversations, and failed selection. Authentication failures are not reported as missing automatic-review support.

## Notifications

When a Claude or Codex conversation in a background tab waits for approval, finishes, or fails, the app shows an OS notification with Electron's `Notification`. Finished and failed turns stay unread until seen. Close, suspend, restart, and automatic suspension check all working and waiting conversations, even when another conversation's error wins the tab badge.

Unread belongs to each conversation, not the whole tab. `src/conversations/seen-conversations.js` matches exact agent and conversation IDs. On tab activation and window focus, and every 1.5 seconds while the focused tab has unread results, the main process reads visible webview frames. This also covers chat editors and switches to already loaded conversations inside a panel. Retained hidden frames cannot clear unread. Tab and focus changes invalidate pending reads; unknown snapshots, failed reads, and reads taking over a second keep unread marks.

The webview snapshot reads the mounted React tree of the visible composer. Claude's input carries a session with `sessionId`, `isLoading`, and `loadFailed` signals. Codex's permission control carries `conversationId` and `hostId`; only local threads match. These are internal extension details. An unknown shape keeps the result unread; a last-opened thread ID or a resume hook is not used as proof of visibility. A successful conversation-row reveal clears only its own result. The helper reports whether it opened the requested Claude conversation, rather than merely focusing the panel. Every completion starts unread and a fresh snapshot clears it if shown; notifications still depend only on tab and window visibility.

On macOS, the app passes only the title and body. Clicks reach the `click` of that `Notification` only while the app that showed it is running. Notifications from before a restart have no way to carry which conversation they belong to, so clicking them does nothing.

On Windows, the app builds the toast (XML). Clicks reach the app by two paths:

- Clicking a notification shown by the app while it is still running: Electron receives the Windows event (`Activated`) and passes it to the `click` of the `Notification` object that showed it. But an object nothing refers to is collected by GC, and its `click` listener goes with it. Windows keeps toasts in the notification center after they disappear, so the app holds on to the notifications it showed until they are clicked. It holds the latest 20. The Windows notification center keeps up to 20 per app.
- Clicking a notification shown before a restart: there is no object, so Windows calls Electron's COM server, which reaches `Notification.handleActivation`. If the app has exited, Windows starts it.
  - Only the toast's `launch` string arrives. Toasts built by Electron have no `launch`, so the app builds the toast XML itself and puts the tab and conversation ids in it (`src/conversations/notifications.js`).
  - Electron registers the COM server the first time notifications are used. So that the click that started the app is also received, the app has it registered right after start. `handleActivation` is registered after the tabs are restored. Electron holds clicks from before that and delivers them on registration.
  - After a restart, the conversations are not known yet, so the app only switches to the tab.

## Shell environment (macOS)

The PATH of an app started from Finder, the Dock, or Launchpad is only launchd's (`/usr/bin:/bin:/usr/sbin:/sbin`). What shell startup files add, such as Homebrew's `/opt/homebrew/bin` and `~/go/bin`, is missing, so ghq, gh, and claude are not found. Without ghq, the repository list is empty.

- As VS Code does, the app reads environment variables from a login shell (`$SHELL -i -l -c`) at start and takes them into its own environment (`src/shell-env.js`). The shell's PATH comes first, and folders only the app has are added after it.
- This is read in parallel with creating the window, and the app waits for it before running the first command (the repository list). If the shell does not answer within 10 seconds, the app keeps its own environment.
- It is read the same way when started from a terminal (`npm start`).

## WSL (Windows)

Inside the app, WSL folders are kept as `\\wsl.localhost\<distro name>\...` paths (`\\wsl$\...` is converted to this form too). git, ghq, gh, and code-server run inside WSL, and the Linux paths they return are converted to this form. Usage is in [wsl.md](wsl.md).

- Windows git cannot read repositories inside WSL (`detected dubious ownership`). git inside WSL can.
- The app runs a small agent (`src/wsl/wsl-agent.js`) inside WSL for each distro. It is written to `~/.worktabs/bin` in WSL and started from `wsl.exe` with code-server's node. It talks with the app over standard input and output, one JSON line at a time.
  - It runs commands inside WSL. Starting `wsl.exe` takes 0.3 to 0.5 seconds each time, and adding a worktree calls git 6 times, so going through the agent is faster. ghq and gh run with the environment variables of the user's shell (`$SHELL -i -l`), so ghq installed in `~/go/bin` and similar places is found.
  - It starts code-server per tab, and when stopping one, stops the processes under it too (extension host, claude, terminals). Stopping `wsl.exe` with `taskkill` leaves the processes inside WSL running. When the app exits (or crashes), the agent's standard input closes, so the agent stops everything it started and then exits.
  - It receives requests from hooks and the helper extension on `127.0.0.1` in WSL and passes them to the app. With WSL's default NAT networking, Windows' `127.0.0.1` cannot be reached from inside WSL. The other direction (from Windows to code-server and the helper extension on WSL's `127.0.0.1`) works through WSL's localhost forwarding.
  - It watches the claude processes that sent hooks and tells the app when they end (to remove the conversation rows). On Windows the app watches the `claude-wrap.exe` processes, but it cannot see processes inside WSL.
- The claude wrapper is the Linux `claude-wrap` (`src/wsl/wsl-claude-wrap.sh`). Like `claude-wrap.exe`, it adds hooks with `--settings` and passes its own process ID in `WORKTABS_PROC_ID`. It replaces itself with claude (`exec`), so that ID is claude's. SessionStart is forwarded through the agent's `hook` mode.
- The transcript and working folder in hooks arrive as Linux paths, so the app converts them to `\\wsl.localhost\...` before reading.
- The Linux code-server has its terminal command only under the name `code-server`. As is, `code` would start the Windows VS Code found later in PATH, so the app creates a `code` symbolic link in the same folder.
- The extensions installed are the same versions as in the Windows tabs. When no WSL tab is running and a version differs, the app reinstalls them (reinstalling removes the old version, so it waits while any tab is running).

## Chat panel focus

When the Claude Code chat panel gets focus, it moves focus to its input box a little later. At that point it does not check whether it still has focus.

- When there are chat panels in both the right panel and an editor tab, and focus moves quickly from one to the other (for example, coming back from another app or the sidebar and clicking the other chat panel), both end up waiting to focus their input box. The two chat panels then steal focus from each other hundreds of times a second, the screen flickers, and you cannot do anything. This continues until the window loses focus.
- So each time a chat panel page (the frame inside the webview) loads, the app adds a rule to focus from scripts (`focus()`). While focus is elsewhere in the page, a chat panel without focus cannot take it.
- Moving focus by clicking, and VS Code handing focus to a chat panel (`window.focus()`), are unchanged. A chat panel given focus moves it to its input box as before.
- While you type in one chat panel, focus does not move to another chat panel even if it shows an approval prompt or similar.

## Throttling

Chromium's background throttling is disabled. With it on, the Claude panel's webview stops in hidden tabs and in windows behind others, and work stops for minutes.

## Updates

`src/code-server/extension-index.js` parses the active extension inventory for local and WSL readers. It exposes lowercase IDs, original identifiers, versions, declared and default targets, relative locations, and location validity. Each operation reads a fresh snapshot, so obsolete folders cannot select an old executable after an update or restore. CLI selection and language packs reject escaping locations. Imports still verify the selected folder and manifest against the index; malformed import metadata is an error. WSL version matching and update discovery tolerate an unavailable index. Local installation reports corrupt-index errors. Gallery and import compatibility policies remain in their callers.

`src/code-server/extension-imports.js` handles desktop discovery, platform and engine validation, complete snapshots, SHA-256 checks, per-target sources, and transactional local imports. The renderer selects opaque candidate IDs, not executable paths. Management IPC is restricted to the settings dialog's web contents. Imported IDs are excluded from Open VSX updates; Codex has no automatic Open VSX fallback. Desktop imports are compared only with their recorded local source. Embedded gallery access is disabled by default. See [extensions.md](extensions.md).

The app relies on internal behavior of code-server and the extensions (the `?folder=` URL, cookie authentication, `languagepacks.json`, how the extension behaves with a wrapper), so the versions are pinned. How to update is in [usage.md](usage.md#updating-code-server-and-extensions).

- code-server is compared with the GitHub releases that have a Windows build, and the extensions with the latest Open VSX version for the same platform as the installed one (win32-x64 and so on). For extensions, only versions that run on the current code-server's VS Code are candidates.
- The releases are read through `gh api` when gh is signed in to github.com, and without signing in otherwise. GitHub answers 60 requests an hour to an address that is not signed in, and an office network shares one address. A failed source does not stop the others: a GitHub limit still shows the Open VSX updates, with the error and the time the limit ends.
- The extensions folder is shared by all tabs. Installing a new version marks the old one for removal, and it is removed the next time any code-server serves a page. That would also remove the version a working tab is using, so updates wait until no tab is working.
- Extensions are installed with the code-server command in use before the update. Rolling back works the same way.
- WSL keeps separate Linux imports. Claude uses its Linux publication rather than a Windows pin; other app-managed extensions retain synchronization where applicable. Prepared imports apply at the next matching WSL start. Transactional snapshot restoration and the hidden probe currently run locally, not in WSL.

## Unsaved edits

VS Code Web defaults to `files.autoSave: afterDelay` (auto save after about 1 second), so edits are rarely lost. In case auto save is turned off, the app checks for unsaved editors before close, suspend, restart, reload, and exit. If there are any, it asks for confirmation, and the tab is also excluded from automatic suspend when idle.

## Isolation of the views and the packaged app

Every view (the tabs, the sidebar, the dialog page) is made with `viewPreferences` in `src/window/web-preferences.js`: context isolation and the sandbox on, Node integration off. These are Electron's defaults; they are spelled out so that a test fails if a change turns one off. The tabs show code-server, a page the app does not control, and the sidebar and the dialog page reach the main process only through what their preloads expose.

The packaged app flips two of Electron's fuses (`electronFuses` in `package.json`): it ignores the `NODE_OPTIONS` and `NODE_EXTRA_CA_CERTS` variables and the `--inspect` arguments, so another program cannot run its own code in the app's process through them. The RunAsNode fuse stays on: on macOS the claude wrapper (`src/agents/mac-claude-wrap.js`) and the login shell's environment (`src/shell-env.js`) run the app's own executable as Node with `ELECTRON_RUN_AS_NODE`. The fuses apply only to `npm run pack` and the builds after it; `npm start` runs Electron as it comes.
